# Accounts, Devices, Authentication, and Recovery

## 1. Separate state machines

Server account: invited -> registered -> active -> disabled/deleted. API session: unauthenticated -> authenticated -> expired/revoked. Device trust: generated -> pending -> approved -> active -> revoked. Local vault: locked -> unlocking -> unlocked -> locked. Do not collapse these states into one loggedIn flag.

A successful server login on an untrusted installation exposes minimal account and enrollment/recovery state only; it cannot enumerate groups or use ordinary content/key endpoints. Local offline unlock does not imply an active server session.

## 2. Account authentication

Passkeys/WebAuthn are primary. Use a maintained Laravel-compatible verifier, strict configured RP ID/origin allowlists, user-verification requirements, one-time challenges, and protection against account enumeration. Allow more than one passkey. Recommend two authentication methods without forcing a purchase.

PWA: Laravel session/Sanctum stateful authentication with an API-host-only __Host-vault_session cookie: Secure, HttpOnly, Path=/, no Domain, SameSite=Strict for this controlled same-site topology. Fetch the API with credentials and exact allowed static-app Origin; no wildcard/reflected CORS. Do not keep session identifiers in localStorage or copy the usual readable XSRF-cookie example blindly across origins [SRC-11].

GET /auth/csrf establishes an anonymous/authenticated session and returns its synchronizer CSRF token in no-store JSON to the allowed app origin via credentialed CORS. Keep that token in page memory and send X-CSRF-TOKEN on state changes including registration/login. Reacquire it after session regeneration. Retain Laravel CSRF middleware and strict Origin/Content-Type checks; configure stateful origins explicitly. No parent-domain cookie is needed. Add Vary: Origin where appropriate. SameSite alone cannot defeat a hostile sibling subdomain [SRC-20].

Windows: use the static app login/consent UI in the system browser and the same WebAuthn RP/origin as PWA. Use a maintained OAuth authorization-code implementation with PKCE S256 and state. Prefer a loopback listener bound only to literal 127.0.0.1 or [::1] on a freshly allocated port, with exact scheme/IP/path validation and permitted dynamic port under the registered native client policy. Never listen on 0.0.0.0 or assume a native public client can keep a client secret. A 60-second single-use code binds client, redirect, PKCE challenge, account, issuer and intended device-key commitment. No tokens in callback URLs; API redirects never supply executable app code. Follow RFC 8252/current OAuth security guidance [SRC-21].

Native credentials stay in Rust-protected storage. Use short-lived access tokens and rotating refresh credentials with reuse detection under the selected maintained OAuth implementation. Store token hashes or nonsecret revocation identifiers as required by that library, not raw reusable refresh secrets in ordinary SQL/logs. Select and record the compatible library in P02/P06; Sanctum personal access tokens alone are insufficient. Upgrade a restricted session only after the enrolled device signs a fresh challenge binding session/account/service. Repeat possession proof on re-login; a client-supplied device ID is not enough.

Default session policy: 15-minute native access token, 30-day maximum refresh/session lifetime, recent authentication within 5 minutes for high-impact account actions. Web server sessions have idle/absolute expiration configured separately and documented; local vault auto-lock remains independent.

## 3. Bootstrap and invitations

Bootstrap invitation generated by an operator-only command, displayed once, stored hashed, single-use, expiring. Subsequent account invitations are administrator-only, 48-hour default expiry, optional intended handle/contact binding. An invitation proves permission to create an account, not ownership of any group identity.

Group invitations are separate signed operations from a group owner, targeted to a verified account root fingerprint, role, group, and membership version. Never share content through an email invitation URL alone. Email, if configured, carries generic invitation/authentication messages only.

## 4. Device enrollment protocol requirements

Each new installation generates independent Ed25519 and encryption keypairs, a random device ID, and a high-entropy enrollment secret locally. Pending requests expire after 10 minutes and are rate-limited. Device labels are encrypted account-private preferences; an opaque ID and platform class may be public metadata.

The enrollment transcript binds service origin/installation, account/root identity, new device public keys, pending session ID, random challenges, expiry, and the approving device. Authentication must come from an out-of-band QR secret/public-key commitment or a reviewed authenticated key-exchange scheme. The API acts only as a relay.

Required user flows:

1. New Windows displays a QR that an existing trusted phone scans.
2. New iPhone scans a pairing QR displayed by an existing trusted Windows app; a reverse bootstrap mode avoids requiring a PC camera.
3. If neither can scan, use a reviewed SAS-based pairing flow with comparison on both devices. A six-digit value is not a password or standalone encryption key; bind it to the complete authenticated exchange, single attempt/session, and user confirmation.

Both devices show matching account, origin, device identity, and confirmation. The new device must authenticate the existing account root through the pairing transcript; fetching a root from the same untrusted relay is insufficient. Only after mutual confirmation may the existing device sign enrollment and send encrypted group-key envelopes. Prevent replay, reflection, cross-account substitution, approval race, and session reuse.

Use an established authenticated channel construction where feasible; P02 must document the selected protocol and exact messages. Do not label an unreviewed QR exchange secure merely because its payload uses AES or XChaCha.

## 5. Device roster and limits

Every account maintains a signed, versioned roster anchored at its root identity. The server validates transitions and clients independently verify them. Ordinary enrollment requires an active authorizing device and current roster parent. Recovery reset is signed by root authority and increments a recovery generation. Exclude old-generation devices from future group-envelope distribution.

Default active-device cap: 5/account, configurable. A full cap results in an actionable device-management screen, not silent eviction. Approval creates a signed provisional certificate only. The new device must confirm possession against the pairing transcript before active roster publication, session upgrade, or group-key release. Confirmation commits atomically against the expected roster head; expired pending approvals cannot receive keys. See file 20. Group keys may arrive progressively after activation, with visible “Waiting for keys” per group.

## 6. Local unlocking

Windows: L and device secrets use an OS-protected wrapper. Evaluate DPAPI/DPAPI-NG/CNG as supported primitives. DPAPI user scope alone does not prove physical user presence and does not protect against malware running as that user. A Windows Hello mode must cryptographically gate access to the actual key operation; a UI-only Hello check in front of an otherwise readable secret is unacceptable.

PWA: persist encrypted device vault only. Use PRF as an optional proven wrapper; offer a strong local unlock phrase as a universal fallback. A device-only passphrase does not enroll a new device or replace account recovery. Non-extractable browser keys cannot be treated as immunity to malicious same-origin JavaScript.

Default auto-lock: 5 minutes of inactivity; lock on Windows session lock/suspend; on iOS backgrounding hide sensitive views and lock for resumed use by default. Persist encrypted pending work before clearing accessible secrets where lifecycle permits. Do not depend on an unload callback for the only durable save. Unsynced edits must be encrypted incrementally during normal editing.

## 7. Recovery kit and procedure

The offline kit contains: checksummed R, account ID, service installation ID, root fingerprint, format version, service URL, instructions, and optional separate account-authentication recovery codes. Authentication recovery codes are independently random, single-use, stored hashed server-side, and do not themselves decrypt content. R is never sent to the server.

Onboarding must ask the user to verify selected kit information before marking recovery configured. Plaintext kit printing/download is an explicit user export. Do not upload the kit as an ordinary unencrypted attachment or email it. The service stores public recovery keys and signed encrypted group-key envelopes only.

Recovery sequence:

1. Re-establish server account access using a passkey, one-time authentication recovery code, or operator-assisted authentication reset. Operator reset does not grant decryption.
2. Enter R only in a trusted client, preferably the installed verified Windows client when service compromise is suspected.
3. Derive root/recovery keys and compare root fingerprint/account/service binding to the kit and stored checkpoints.
4. Generate new device keys, obtain a short-lived recovery challenge, and root-sign its account/service/session/new-key/current-generation context. Publish a compare-and-swap recovery reset. The server checks the already registered root, consumes the challenge, activates the fresh device, revokes previous devices/sessions, and upgrades only this recovery session atomically.
5. Now retrieve this account's recovery-recipient envelopes for currently authorized groups through the trusted device. Validate/decrypt locally and issue fresh envelopes for it. Groups from which the account was removed do not become available again through service recovery; independent old exports may still contain past authorized content.
6. Trigger group rekeys, refresh wrappers, and sync. Reset does not wait for group keys or completed group rekeys, avoiding a recovery deadlock. Writes remain blocked until key-holding current members finish required maintenance. Clear R/root private material as practical.

If all keys/R are lost, personal data is unrecoverable. A group owner may invite a replacement identity into shared groups after independent verification; this is new membership, not cryptographic recovery of the old identity.

## 8. Revocation and compromised recovery

Compromise revoke requires a trusted surviving device or root recovery. Revoke the target, all transitively delegated devices, their sessions, and pending approvals; show the affected set. A surviving device may re-enroll known-safe hardware with fresh keys, never silently preserve attacker-created descendants. Root recovery resets every old-generation device. Mark affected groups rekey-required immediately.

Preserve unsynced local drafts before cooperative cleanup. A revoke notice never authorizes automatic erasure of the only local copy. Lost-device data cannot reliably be erased remotely. Sign-out revokes a session and locks local content; device revoke and explicit local erase are separate actions.

For a merely lost paper kit with no suspected exposure, a kit can be reproduced from R only if R is available; everyday devices intentionally do not retain R. If R is exposed, replacing wrapper passwords is insufficient. Treat as root compromise, use the documented new-identity migration procedure, and require group-owner verification.

## 9. Security UI

Show device name, platform, enrollment date, last server contact, current session, and revoke action. Last contact/IP is metadata, not trustworthy proof that the physical device is safe. Send generic security notifications for new devices, recovery, added passkeys, and membership changes. Do not expose other accounts' private device labels or private groups.

## 10. First-account bootstrap

POST /accounts/register completes invitation consumption, verified authentication enrollment, root-signed public identity, root-certified first device and initial roster as one validated transaction. The first device proves possession against the registration challenge. Upgrade only that bound session; a supplied device ID without proof cannot activate it. Retried registration returns its receipt without consuming another invitation or producing a second identity. Interrupted incomplete authentication enrollment expires without granting content access.

Once the first device is active, create its encrypted account-private settings group with normal signed genesis and recovery envelopes before syncing device labels/preferences. Bootstrap is unavailable once an identity/roster exists; subsequent devices use enrollment or recovery reset. A service operator cannot invoke bootstrap to replace an existing root.
