# Synthetic Windows PRF/TPM probe

This is an isolated native experiment adapted from the owner-confirmed
passkeylocal installer source `c18894e210a07546ba66cf178b8048ae5c40ac61`.
It uses random synthetic local key **L**, not a KDBX password component or a
production content key. No frontend, password, account, raw-key IPC or arbitrary
path/RP/key-name interface exists. Do not use real data or secrets.

## Build and actual checks

Windows x64: Rust 1.99.0 MSVC, Microsoft C++ Build Tools and Windows SDK.
Native crates and exact dependencies are locked. Native sodium's bundled signed
inputs retain verification. From this directory:

```powershell
rustup toolchain install 1.99.0 --profile minimal --component clippy,rustfmt
rustup override set 1.99.0
./tests/hello/webauthn-layout.ps1
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo test --locked generated_layout_matches_the_pinned_microsoft_c_header -- --ignored
cargo build --locked --release
./target/release/anynote-p01-windows-hello.exe capabilities
```

The explicit ignored test compares generated Rust layouts to a separately
MSVC-compiled official C header. Its omission is not an ABI pass. The header
SHA-256 must be `da82d5be6b90a2706185ae44ad93649bcefc0f89c97ab930ec4e6f0abb7b2283`;
Git preserves its original bytes. Public W3C authenticator-data fixtures were
regenerated by the independent Python struct/P-256 generator for AnyNote's RP;
the parser's offsets are not used to generate expected bytes.

Hosted Windows CI builds/tests the actual native code and records **capability
only**. It creates no passkeys or TPM keys. An unavailable API/Hello route is an
observation, not physical success. Linux runs portable policy/lifecycle tests;
the executable itself exits 2 with BLOCKED on Linux. Local GNU cross-checking
is optional and needs a MinGW compiler; it is not a substitute for MSVC/runtime.

## Disposable physical trial

Target supplied by the owner: Windows 11 Pro 25H2 with Windows Hello planned.
Capture the actual OS build/API, authenticator, probe source and executable hash
during a new AnyNote trial. Use the existing account; no reset or security-policy
change is required. Preserve upstream completed experiments and exclusions.

[The owner runbook](../../../docs/P01_OWNER_TRIALS.md) gives a frozen successful
EXE hash/source and the content-free collector. `scripts/collect-physical.ps1`
verifies that hash/source, captures actual OS/model/RAM, gates enrollment/unlock
on capabilities and preserves failed operation exit status. Its hosted CI record
is labeled hosted and cannot certify physical acceptance.

```powershell
Get-FileHash ./target/release/anynote-p01-windows-hello.exe -Algorithm SHA256
./target/release/anynote-p01-windows-hello.exe roundtrip
```

`roundtrip` creates a real native window and registers Windows lock/suspend
notifications. Closing or lock/suspend invalidates in-flight work. It creates a
fresh encrypted synthetic vault, journals ownership before native object
creation, enrolls and verifies a separate fresh authorization round trip,
explicitly unlocks, authenticates the actual vault and cleans up exact objects.
Several OS prompts may occur. Cancel must not unlock or silently retry.

For fresh-process testing, run `enroll` (explicit experimental remember6 mode),
then `unlock` in a new process, then `cleanup`. An existing journal/vault prevents
replacement enrollment. Failed deletion leaves a durably non-ready journal for
`cleanup` retry. Never delete that journal to hide cleanup failure. Only the fixed
`%LOCALAPPDATA%/AnyNoteP01Hello` synthetic state and journal-owned native objects
are addressed; commands accept no caller paths or native object identifiers.

The native adapter loads WebAuthn from System32, requires API 9+ routing, PRF
creation-time evaluation and fresh UV, verifies exact credential context and
rechecks the Platform KSP TPM public area/Name on reopen. The outer envelope is
HKDF-SHA256/AES-256-GCM(PRF) over inner TPM RSA-2048 OAEP/SHA256 ciphertext.
New RP/domain/key/journal namespaces prevent interaction with passkeylocal.
Secrets stay in native memory; the key-bearing internal reply cannot serialize.

Every unlock must additionally authenticate the unchanged real synthetic-vault
ciphertext before reporting success. Diagnostics contain no key, PRF result,
credential ID, enrollment envelope or key name. `physical_acceptance:false` means
the complete platform matrix has not been certified, even if a particular real
operation succeeds. Reports distinguish unavailable/cancelled/failing operations.

This trusts Windows/KSP/TBS and the running process; local ReadPublic evidence
is not remote attestation or protection against an administrator/kernel attacker.
There is no DPAPI/software/consent-only fallback. Imported Passport diagnostic
helpers are not CLI actions or alternative unlock methods. Independent AnyNote
recovery, production vault/session integration, WebView2 IPC and comprehensive
physical expiry/revoke/lifecycle acceptance remain future gates.
